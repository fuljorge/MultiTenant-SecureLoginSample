# OWASP ASVS Level 2 checklist — identity and access (T076)

- **Feature:** 001-identity-access · **Standard:** OWASP ASVS 4.0.3, level 2 · **Chapters:**
  V2 (authentication), V3 (session), V4 (access control)
- **Date:** 2026-10-04 · **Filled in by:** coding agent, for human review
- **Legend:** ✅ met · ⚠️ partially met (see open item) · ➖ not applicable

Authentication is handled by Keycloak 26.7.5 (realm `infra/keycloak/realm/cap-realm.yaml`);
the browser session and authorization are handled by the Control Plane (BFF pattern; plan,
sections 4.1 and 4.2).

## V2 — Authentication

| Item | Requirement (summary) | Status | How it is met / evidence |
|---|---|---|---|
| 2.1.1 | Password of 12+ characters | ✅ | `length(12)` in the realm; minimum cannot be relaxed from the security settings screen (`security_settings.py`) |
| 2.1.2 | Accept 64+ and reject 128+ characters | ✅ | Fixed `maxLength(128)`; `test_politica_aceita_64_e_recusa_mais_de_128_caracteres` |
| 2.1.3 | No truncation | ✅ | Keycloak Argon2 hash over the whole password |
| 2.1.4 | Any Unicode character | ✅ | Policy with no character restrictions |
| 2.1.5 | Users change their own password | ✅ | "Change password" menu (`GET /auth/password`, `UPDATE_PASSWORD` action) |
| 2.1.6 | Change requires the current password | ✅ | Changing one's own password always asks for a new authentication, with password and code (`prompt=login`, `max_age=0`; RF-031); `test_troca_de_senha_sempre_reautentica` |
| 2.1.7 | Reject breached passwords | ✅ | `passwordBlacklist` with the Pwdb top 1M list (research R5); `test_politica_recusa_senha_vazada` |
| 2.1.8 | Password strength meter | ✅ | Indicator in the Keycloak `cap` theme, on the set and change password screens (RF-032); activation E2E |
| 2.1.9 | No composition rules | ✅ | Only length, breached list, history and "different from the e-mail" |
| 2.1.10 | No mandatory periodic rotation | ✅ | No expiry policy |
| 2.1.11 | Paste and password managers allowed | ✅ | Standard theme fields, paste not blocked |
| 2.1.12 | Show the typed password | ✅ | "Show password" button in the `cap` theme |
| 2.2.1 | Brute-force protection | ✅ | 15 min lockout after 5 password **or code** failures (finding A15, patch); realm tests |
| 2.2.2 | E-mail only as a secondary factor | ✅ | The e-mail code is the second factor, after the password; stronger factors (authenticator app, security key) planned for a future phase (spec, out of scope) |
| 2.2.3 | Notify the user after a credential change | ✅ | Password-changed e-mail (worker, RF-005) and notice to the old address on e-mail change |
| 2.3.1 | Random, expiring initial credentials | ✅ | Single-use activation (72 h) and recovery (30 min) links; no initial password is sent |
| 2.4.1–2.4.5 | Password storage | ✅ | Delegated to Keycloak (Argon2); the Control Plane never receives passwords |
| 2.5.1 | Activation does not send a secret in clear text | ✅ | Single-use link only |
| 2.5.2 | No hints or secret questions | ✅ | None exist |
| 2.5.3 | Recovery does not reveal the current password | ✅ | Recovery via Keycloak link |
| 2.5.4 | No shared or default accounts | ✅ | The `cap` realm has no default accounts (`test_realm_sem_administradores_ou_clientes_extras`); the `master` realm bootstrap administrator is temporary in every installation (provisioning requirement, §53.2) |
| 2.5.5 | Notify when the authentication factor changes | ✅ | Same as 2.2.3 |
| 2.5.6 | Secure recovery | ✅ | Single-use, time-limited link; same response whether the e-mail exists or not (`test_enumeration.py`) |
| 2.5.7 | Loss of factor requires re-identification | ✅ | E-mail change confirmed by the new address; Super Administrator without e-mail access: `cap-admin reissue-activation` with a support ticket and identity verification |
| 2.7.1 | No SMS or phone by default | ✅ | E-mail only |
| 2.7.2 | Code expires within 10 min | ✅ | 10 min (configurable maximum: 15 min) |
| 2.7.3 | Single-use code | ✅ | Consumed on login and invalidated after 5 attempts (patch A15) |
| 2.7.4 | Secure channel to the authenticator | ✅ | SMTP with mandatory TLS in every installation (provisioning requirement, §53.2; `KC_SMTP_STARTTLS`, `smtp_starttls`); only the local environment uses Mailpit without TLS |
| 2.7.5 | Code stored only as a hash | ✅ | SHA-256 in the authentication session, constant-time comparison (research R1, item 1) |
| 2.7.6 | Code from a secure generator with 20+ bits | ✅ | Keycloak `SecretGenerator`, 6 digits (~20 bits), with attempt lockout |
| 2.8.x | App or device OTP | ➖ | Not offered in this phase |
| 2.9.x | Cryptographic verifier | ➖ | Not offered in this phase |
| 2.10.1 | Service-to-service secrets outside the code | ✅ | Environment variables generated by `init_env.py`; encryption key in OpenBao |
| 2.10.2 | No default service-to-service credentials | ✅ | All randomly generated per installation |
| 2.10.3 | Service credentials protected | ✅ | In production, injected by OpenBao or cluster secrets (provisioning requirement, §53.2); locally, `.env` kept out of Git and the image (`.dockerignore`) |
| 2.10.4 | Secrets outside the source code | ✅ | gitleaks in pre-commit and CI |

## V3 — Session

| Item | Requirement (summary) | Status | How it is met / evidence |
|---|---|---|---|
| 3.1.1 | Session token not in the URL | ✅ | Cookie only |
| 3.2.1 | New token on every authentication | ✅ | Session created in the login callback |
| 3.2.2 | 64+ bits of entropy | ✅ | 256 bits (`secrets`); Valkey stores only the SHA-256 |
| 3.2.3 | Token only in a secure cookie | ✅ | Keycloak tokens stay on the server, encrypted by OpenBao Transit |
| 3.2.4 | Cryptographic generator | ✅ | `secrets` module |
| 3.3.1 | Logout invalidates the session | ✅ | BFF and Keycloak; back-channel logout |
| 3.3.2 | Periodic re-authentication | ✅ | 30 min idle and 12 h maximum, in the BFF and in Keycloak; the security settings screen rejects a maximum session above 24 h |
| 3.3.3 | Terminate other sessions on password change | ✅ | Every password change terminates **all** sessions (RF-005) |
| 3.3.4 | View and terminate one's own sessions | ✅ | "My sessions" (RF-006) |
| 3.4.1 | `Secure` attribute | ✅ | `cookies.py` |
| 3.4.2 | `HttpOnly` attribute | ✅ | On the session cookie; the anti-CSRF cookie is readable on purpose (double submit) |
| 3.4.3 | `SameSite` attribute | ✅ | `Lax` |
| 3.4.4 | `__Host-` prefix | ✅ | `__Host-cap_session`, `__Host-cap_csrf`, `__Host-cap_login` |
| 3.4.5 | Path scope | ✅ | `Path=/`, no `Domain` |
| 3.5.1 | Revoke OAuth tokens | ✅ | Ending the session deletes the stored tokens and logs out of Keycloak |
| 3.5.2 | Session does not use a static secret | ✅ | Session per person and per login |
| 3.5.3 | Stateless tokens signed and validated | ✅ | ID token validated (RS256, realm JWKS, `nonce`) with joserfc |
| 3.7.1 | Re-authentication before sensitive actions | ✅ | The 17 RF-031 actions require a full login no older than 15 min (`require_recent`); list checked against the contract; `test_recent_auth.py` and user management E2E |

## V4 — Access control

| Item | Requirement (summary) | Status | How it is met / evidence |
|---|---|---|---|
| 4.1.1 | Rules enforced on the server | ✅ | `require`/`require_any` on every route and RLS in PostgreSQL; structural route test (T058) |
| 4.1.2 | Authorization attributes cannot be tampered with | ✅ | Role and organization come from the database on every request, never from the client |
| 4.1.3 | Least privilege | ✅ | Spec matrix (section 5.1) read by the test; Super Administrator without access to organization content (RF-028) |
| 4.1.5 | Fail securely | ✅ | Deny by default; a route without declared protection fails CI |
| 4.2.1 | Protection against direct object access (IDOR) | ✅ | Per-organization RLS; a resource from another organization returns 404 and emits `access.denied` (`test_cross_org.py`, `test_super_admin_rls.py`) |
| 4.2.2 | CSRF protection | ✅ | `X-CSRF-Token` header (double submit) and `SameSite=Lax` |
| 4.3.1 | Administrative interfaces with MFA | ✅ | Second factor mandatory for everyone, administrators included |
| 4.3.2 | No directory listing or exposed metadata | ✅ | `/docs` and `/openapi.json` disabled by default (`CAP_API_DOCS`); no directory served |
| 4.3.3 | Segregation of duties in high-value systems | ✅ | Super Administrator separate from organization roles, with a *trigger* that prevents membership (RF-028); last Administrator and last Super Administrator protected (RF-012) |
